# Codexからjrgを使う取得手順

## 0.15.4: 必要な根拠を保って取得範囲を絞る

取得前に、答えに必要な振る舞い、条件式の全節、後処理・呼出し先、関連テストを定める。既知の識別子とパスには狭い`review`、特定の定義・条件には`explain`を使い、返された具体的な不足範囲だけを`read`する。関数が既知なのに1〜300行などの範囲を推測して先読みしない。必要なら小さなモジュール全体を読む。一括取得は独立した必要範囲をまとめるために使い、周辺コードを予測で大量取得するためには使わない。

複数の確認項目には`requirements`を付け、返却された条件式・実装・テストを項目ごとに確認する。これは原文との対応付けであり、`matched`だけでは意味上の十分性を保証しない。依存先・テストの省略案内、`unresolved`、`conditions_incomplete`、`syntax=unavailable`、`pending`、`capture_omitted`を確認する。トークン削減のために必要な条件を落とさない。

範囲を絞ってから`max_tokens`を調整する。この予算はMCPの返却本文だけであり、外側ツールの出力上限や別の結果を含まない。大きな取得結果と別版のファイル全文・大量の一覧を一つの外側出力へ混ぜない。版比較には範囲を限定した差分を使う。内側の省略と外側の切詰めを両方確認し、不足があれば必要範囲を追加取得するか予算を増やす。

同じ接続では返却済みの行を抑制する。外側の切詰めや会話の圧縮で原文を失った場合、同じ広い検索を繰り返したり取得済み状態を消すために再接続したりせず、必要範囲だけを`repeat:true`で回収する。

```json
{
  "operations": [{"read": {"path": "src/delivery.rs", "start": 40, "end": 85}}],
  "repeat": true,
  "max_tokens": 3000
}
```

パスと行は実際の返却案内に合わせる。新規の不足範囲は通常の`read`で取得する。空の`operations`と`resume:true`は`pending`だけを回収し、`unselected`や`scope_limited`は具体的な範囲を指定する。既出の条件式だけなら、範囲を限定した操作と同じ`requirements`を再送しても再表示できる。

説明は起動時指示、ツール説明・引数説明、プロジェクトの`AGENTS.md`、Codex導入時の共通指示へ反映する。ソース変更後は再ビルド・導入が必要で、起動済みMCPは再接続後に反映される。説明の改善はAIの遵守や実タスク全体の費用削減を保証しない。検証では単なる応答サイズだけでなく、必要な条件式の全節・実装・テストの保持と、失った原文の範囲限定回収を確認する。

## 0.15.3: MCPの誤用防止と修正案内

AIへ使い方を伝える経路は、initialize応答の`instructions`、`tools/list`のツール説明、`inputSchema`内の項目説明・使用例、失敗時の修正案内。クライアントがどこまでモデルへ渡すかは実装によるため、重要な指定方法は複数の経路で伝える。説明だけでAIの遵守を保証することはできない。

`retrieve`は外側の`operations`に`search`または`read`を指定する。検索文字列は`search.patterns`で、外側の`query`ではない。`rank_query`は候補の順位付けだけに使う。検索パスはinitializeで返る設定rootからの相対パスで、既存のファイル・ディレクトリを指定する。ファイル名が不明なら既知の親ディレクトリと`search.globs`で絞り、結果に現れたパスを読む。空の`paths`を送らず、rootを対象にする場合は`paths`を省く。

`review`はスコープ単位で原文を選ぶので`context`を省く。互換性のため0〜128の値を受け付けるが無視し、取得範囲を変えない。不正な型・範囲は引き続き拒否する。未知の引数・空配列・存在しないパスは対象項目と修正方法を返す。存在しないパスを自動でroot全体の検索へ置き換えることはない。root外やシンボリックリンクによる脱出も引き続き拒否し、権限内の通常ツールを案内する。

`inputSchema.examples`の検索・調査・範囲読取の例を実際のMCPサーバーへ送る回帰テストを用意した。使用例のパスと識別子は対象プロジェクトに合わせる。導入済みバイナリの更新後、起動済みの接続は再接続が必要。新しく起動したMCPの版・使用例・検索成功を個別に確認する。

## ローカルの検索履歴と評価

smart/MCP検索は既定で検索条件と実際の返却範囲を記録する。`retrieve`の`structuredContent.history`にIDがあれば、実際の利用で役立った根拠が得られた後に`feedback`へ`request_id`、`result_id`、`label`、再試行で同じ`event_id`を渡せる。検索時と評価時に同じタスクの`context_id`を使う。単に一致した、出力された、検索が成功しただけでhelpfulを付けない。MCPの評価は常にagentであり、人の確認とは区別する。

同条件の候補順位だけに反映し、現在の原文を毎回照合する。`history_mode=record`は比較用の記録のみ、`off`は記録・反映とも無効。要求項目IDと検索結果IDは別。取得済み範囲を扱う`session`も履歴とは独立している。[CLI・保存先・worktree・編集後の対応条件](HISTORY.md)を参照。

## 0.15.2: MCPとクライアントの優先方針

MCPのinitialize応答の`instructions`とretrieveの説明の先頭で、設定root内のコード調査・内容検索・範囲を限定した原文取得にjrgを優先する方針を伝える。先頭512文字以内にrgの例外と利用不可時の通常ツールへの切替も含める。全一致・全ファイルの列挙、不存在確認、正確な件数、機械出力・パイプ処理、未対応のオプション・エンコードは通常のrgを使う。rgの実体・aliasや既存の権限を変更しない。

このプロジェクトでは、CodexとOpenCodeは`AGENTS.md`、Claude Codeは`CLAUDE.md`から同ファイルをimport、Cursorは`.cursor/rules/jrg.mdc`の`alwaysApply: true`で常時ルールを読み込む。MCP接続先はCodexの`.codex/config.toml`、Claudeの`.mcp.json`、Cursorの`.cursor/mcp.json`、OpenCodeの`opencode.json`へ登録し、同じ起動スクリプトと導入先バイナリを使う。Claudeではこの利用者のプロジェクト専用ローカルMCP登録も公式CLIで行い、共有設定の初回承認待ちを残さず接続を確認した。

接続設定の絶対パスは今回のローカル環境用で、別の環境ではパスを合わせる。別プロジェクトへのグローバル登録は行っていない。起動スクリプトは接続ごとに新しいseen/pending状態を作り、同じ接続内で共有する。更新前から動いているMCP接続は再接続、新しい常時ルールはクライアントの再読込みまたは新しい会話で反映する。

これらは優先方針をモデルへ伝えるもので、全クライアントが必ずjrgを選ぶ強制機構ではない。追加モデルなしの検証では、設定の読戻し、MCP初期化指示、実際のretrieve、条件式・取得済み状態・rg経路を確認する。モデルによる選択率や実利用での速度差は別の測定とする。

検索結果がjrg内の予算に収まっても、内側exec_commandや外側functions.execの上限で切れることがある。外側・内側の両方を設定する。jrgの既定24,000は維持し、不要な範囲を先に絞る。

1回の一括取得を返すfunctions.execの例:

```javascript
// @exec: {"max_output_tokens": 30000}
const result = await tools.exec_command({
  cmd: "jrg --smart --batch request.json",
  max_output_tokens: 26000
});
text(result.output);
```

先頭のpragmaが外側の上限を設定する。`exec_command`の引数だけでは外側の10,000は変わらない。`text(result)`で結果全体をJSON化すると改行がエスケープされ、本文以外の情報も増えるため、`result.output`を返す。終了コードは呼出し側で確認し、非ゼロなら短く表示する。

独立した複数コマンドを同じセルで返す場合は、内側の出力上限の合計を26,000以下にするか、外側を合計＋余裕分へ増やす。上限が十分でも実行環境がさらに制限する場合があるため、切詰め通知を確認する。巨大なファイル一覧は対象ディレクトリ・globで絞り、内容の読取と混ぜない。予算に合わせて原文を黙ってheadで捨てない。

## 0.15.0: 依頼項目と根拠・条件の対応

0.15.1では取得順・候補枠・返却形式を維持し、統合と予算整形の再計算を削減する。構文解析は拡張子と原文全体が同一の結果だけを再利用し、条件式と関数範囲を同じ解析から得る。キャッシュはスレッドごとに最大32件・原文と解析結果の容量見積り16MiB以内で、構文エラーも同じ原文に限り再利用する。上限を超える原文も解析は行い、保持を省く。ファイル読取や取得済み状態はキャッシュせず、内容変更の検査は従来どおり行う。

埋込み済みo200kトークナイザーはプロセス内で共有する。予算判定では、o200kの正規表現の区切りをまたがない領域の正確な計数を1回の整形内で再利用する。単純な文字数換算や任意の断片のトークン数加算は行わない。計数キャッシュは原文キー2MiB・8,192件までで、上限到達後も未登録部分を通常どおり計数する。全体予算・96,000バイト上限・条件式の一括表示・最終表示行だけのseen記録を維持する。並列化やモデル実行は追加しない。

複数項目の調査では、`retrieve`の外側に`requirements`を付ける。依頼の番号を`id`として維持し、`description`に項目、`patterns`に原文の識別子・条件の文字列を指定する。CLIでも`--smart --batch request.json`のJSONに同じフィールドを指定できる。

```json
{
  "requirements": [
    {"id": "R4", "description": "結果の状態・件数・次ページ・版の検証", "patterns": ["result.status", "result.candidates", "result.total", "result.version", "next_offset"]}
  ],
  "operations": [
    {"search": {"patterns": ["receive_parcels"], "paths": ["src/parcels.rs"], "intent": "explain"}}
  ]
}
```

先頭に全項目の状態と、`# evidence R4 path:開始-終了`／`# condition R4 path:開始-終了`に続く行番号付き原文を返す。Rust・Python・TS・JSの`if`／`while`条件をast-grepで取り出し、取得行への一致・真の分岐内の構文上の包含関係で結び付ける。一部の節だけが一致しても複数行の条件式をまとめて優先表示する。条件式内で一致する指定文字列の種類が多い順に、各項目を巡回して確保する。複数項目で同じ原文を参照するときは`shared_source`で先に表示した原文を共有する。`else`の条件の反転、データフロー、型、テストの意味解決は行わない。コメントや文字列への一致も含む。

- `state=matched`／`matches`は取得範囲内の大文字小文字を区別した原文固定文字列の一致。正規表現や日本語正規化を行わず、意味上の裏付け完了を表さない。`unresolved`は今回の選択範囲に一致がない状態で、不存在の証明ではない。
- `conditions`は結び付いた条件式の数。`conditions_incomplete`は式の一部が選択範囲外にある数で、参照に`not_fully_retrieved`を付ける。指定read範囲を勝手に広げない。
- `omitted`は対応表の詳細レコードを予算で省略した数。式を途中で切って完全な条件として見せない。通常の原文欄にも関連行がある場合があるため、必要な条件は参照範囲を狭くreadする。`pending`は実際に未表示の原文行だけで、対応表の省略数とは異なる。
- `syntax=unavailable`は未対応拡張子や構文エラーで条件を解析できなかった状態。文字列の根拠は返すが、条件なしと判断しない。
- 対応表も総トークン予算と96,000バイト上限に含む。詳細は原則予算の1/3・最大2,048トークンとし、全項目の状態を優先する。状態と既存フッターが入らない予算は実行前に拒否する。1〜16項目、idはASCII英数・`_`・`-`の1〜32文字で重複不可。説明は160文字、各項目の固定文字列は1〜16個・各128文字まで。制御文字と空白だけの値は拒否する。
- 条件式は既読でも対応表で再表示する。今回の操作が選択した範囲だけが対象で、過去の全取得結果を自動で再検索しない。`resume`との併用は拒否するため、必要範囲を明示した操作へ付け直す。取得済み管理と、外側のツールで切れずに届いたことの区別は維持する。

回答前に全項目の根拠と条件の各節を照合し、省略や未確認点を回答に残す。対応表は取得済み条件を見つけやすくする機能で、回答側の説明漏れがなくなる保証ではない。`requirements`を省略した既存の取得形式は維持する。

## 調査段階を減らす

- 初回の内容取得で、必要な実装と関連テストを独立操作としてまとめる。既知のファイル・範囲は直接readし、行数確認だけの往復を避ける。
- 広い正規表現はlocateで候補を見つける。explainは関数名・ガード・結果の確認に使う。既定autoが過剰な関数展開を抑制し、全一致点は残す。
- `scope_limited`は局所範囲を選んだ表示。関数全体が必要なら`scope_read`の範囲をreadするか`--explain-scope full`を使う。`pending`とは別である。
- すべての要求項目を裏付けられたら、行番号を付けるだけの読直しや、まとめる前の念押しを追加しない。全件・不存在の確認には完全検索を使う。
- 出力が切れた場合、CLIの取得済み管理をそのままモデル既読と扱わず、必要範囲を`--repeat`で再取得する。

これは呼出し手順であり、外部ツールが実際に適用した上限や、モデル応答回数の削減をCLIだけで保証する機能ではない。実タスクでは切詰め・必要項目・総入力・応答・経過時間を確認する。

## 0.8.0: 構造化したMCP呼出し

`jrg --smart --mcp --root /absolute/project --session /private/tmp/task-session.json`
は、検索と読取だけを提供するstdio MCPサーバーを起動する。追加ランタイム・ネットワーク・シェル実行は不要。セッションの親フォルダは先に作り、会話ごとに新しいファイル名を使う。別バージョンのセッションは引き継がない。

Codexの接続には`mcp_servers.<name>.command`と`args`を使う（[公式設定](https://learn.chatgpt.com/docs/extend/mcp#stdio-servers)）。今回の比較では`codex exec`より後ろの実行ごとの`-c`で接続し、`mcp_servers.jrg.required=true`を指定する。ユーザー全体の設定を変更しない。`codex mcp get`の設定表示だけでなく、app-serverのツール一覧と実際のMCP呼出しで接続を検証した。

ツール`retrieve`へ次のように直接引数を渡す。これは引数の例であり、シェルの文字列や標準入力用JSONを組み立てる手順ではない。

```json
{
  "operations": [
    {"search": {"patterns": ["rg_eligible"], "paths": ["src"], "regex": true, "intent": "explain"}},
    {"read": {"path": "tests/smart.rs", "start": 1, "end": 120}}
  ]
}
```

- `patterns`は既定で日本語正規化を行う固定文字列。`regex: true`は原文正規表現。正規表現のバックスラッシュも引数の文字列として一度だけ渡す。
- `paths`省略時は固定root。`globs`、`case_insensitive`、`context`、`full_scope`を任意指定できる。明示`context`は従来どおり範囲展開より優先する。
- 1呼出しで最大64操作。既定24,000トークン、`max_tokens`は64〜26,000。検索と読取を統合し、取得済みの重複行を抑制する。`operations: []`と`resume: true`で未表示分を取得する。必要な既読範囲だけを再表示する場合は通常操作と`repeat: true`を使う。
- ツールの返却はMCPのcontent.text。functions.exec経由なら先頭30,000のpragmaを引き続き指定し、ツール結果全体をJSON文字列化しない。サーバーの書出し成功は、外側で切れずにモデルへ届いた証明ではない。
- `--session`指定時、MCP応答の書込・flushが成功してから取得済み範囲を保存する。保存するのは原文パス・内容の指紋・範囲で、原文本文は保存しない。
- 指定root外のパスと、外へ出る明示シンボリックリンクを拒否する。パスの付替え競合に対するOSのセキュリティ境界ではない。ホスト側の権限も必要になる。
- ファイル一覧、完全な不存在確認、機械出力は従来のrg経路を使う。MCPは任意CLI引数や任意コマンドを受け付けない。初期版の対応範囲は検索・UTF-8行読取で、すべてのrgオプションを公開していない。

explainのautoでは、同じ検索で定義の宣言部分に一致した場合、その定義は従来の字句範囲上限内で全体を返す。一方、他の一致箇所は呼出し元の宣言と前後3行を返し、大きな呼出し元関数全体へ展開しない。定義と呼出し箇所が別ファイルでも適用する。定義が選択されない条件分岐の検索、明示文脈、`full_scope: true` / `--explain-scope full`は従来の範囲選択を保つ。字句解析による推定であり、識別子の意味解決・依存関係や関連テストの自動収集ではない。実装と関連テストを同じoperationsへ指定することで独立した取得をまとめる。

stdioのメッセージと初期化は[MCP公式仕様](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports)に従い、1行1JSON-RPC、stdoutはプロトコル専用、診断はstderrへ出す。

### 比較後に分かった呼出し手順の注意

0.8の実モデル比較では、ツールを探すためだけの応答が4課題に入り、汎用の検索・発見ツールの説明まで返して入力を増やした。接続を事前検証し、サーバー名を`jrg`に固定した場合は、既知の`tools.mcp__jrg__retrieve`を最初の内容取得から使う。全ツール一覧やスキーマを調査本文として表示しない。接続確認が必要なら、モデルを起動する前にapp-serverのMCP一覧で確認する。次はjrgプロジェクト用の例。

```javascript
// @exec: {"max_output_tokens": 30000}
const result = await tools.mcp__jrg__retrieve({
  operations: [
    {search: {patterns: ["rg_eligible"], paths: ["src"], regex: true, intent: "explain"}},
    {read: {path: "tests/smart.rs", start: 1, end: 120}}
  ]
});
for (const item of result.content ?? []) {
  if (item.type === "text") text(item.text);
}
```

存在を確認したパスを使う。0.8では存在しないパスを1操作へ指定すると、その一括要求全体を実行前に拒否する。外部パスや不正引数の拒否とは別に、ファイル不存在を操作単位のエラーにして他の有効操作を返す改善は今後の候補になる。

この注意は今回の比較後に追加した。名前を固定した初回呼出し手順のモデル応答削減率や、上記の操作単位エラーへの変更は再測定していない。今回の計測結果をこれらの改善後の数値として扱わない。


## BM25のMCP指定

候補が多い検索ではretrieveの外側に`rank_query`を指定できる。検索語・pathsは候補の取得に使い、rank_queryは取得済み候補のBM25関連度に使う。英語のコードには具体的な英語識別子・条件を含める。翻訳や意味検索は行わない。

0.9.0では、ディレクトリまたは複数ファイルを対象にしたlocateを広い探索として扱い、新しい候補の上位12範囲を操作ごとに返す。外側の`discovery_limit`（0〜256）で調整でき、0で制限を解除する。約4,000文字で区切った原文範囲の数であり、行数ではない。候補収集の安全上限は別に維持する。検索前にpathsとglobsを絞る。

read、単一ファイルのlocate、explainの必要な関数・条件分岐は候補制限しない。広い探索とまとめた呼出しでは、これらを先に返す。既定24,000・最大26,000の枠は維持する。予算超過、収集上限、scope_limitedは別の制約であり、全関数・依存関係の取得を保証しない。

`discovery_omitted`は意図的に外した探索候補で、予算不足のpendingではない。最大16件の未選択範囲を予算内で案内する。必要な範囲だけをreadか単一ファイル検索で取得し、広い探索全体をresume/repeatしない。取得済み行を選別前に除くため、再探索でも同じ候補だけで上位枠を埋めない。すでに返した原文と行番号は再利用し、repeatは原文が現在の文脈から失われたときなどに限定する。

独立した既知の実装・関連テストをまとめ、対象が未確定の汎用語の検索はlocate、特定した関数・ガードの確認はexplainとする。広い検索語でexplainを使うと関数展開が増える。rank_queryを省略した要求には順位付け・候補制限を持ち越さない。

## 0.10.0: reviewによる実装・関連テストの一括取得

最初の内容取得からsearchの`intent:"review"`を使う。対象が未確定でも有効なrootの`.`を指定でき、一覧のためだけの往復は不要。具体的な英語識別子・条件語をpatternsとrank_queryへ含め、キーワードの場合はcase_insensitiveも利用する。独立した実装・条件のreviewを同じoperationsへまとめる。

reviewは一致関数／分岐と関連テストを返し、同じファイルの参照先の小さな補助関数・定数・型を添える。テストは実装ファイル名との対応を先に使い、対応を確認できない実装識別子は作業root内の探索で補う。関係はヒューリスティックで、外部ファイルの全依存関係や全テストの閉包ではない。Rustのtest属性、TypeScript/JavaScriptのtest/it、Pythonのtest_を認識し、テストファイル内の補助関数をテスト件数へ混ぜない。

0.10.0時点では1操作あたり実装8・テスト6範囲、補助関数／小さな型8件、定数16件、候補ファイル64件という収集上限を持つ（0.11.0の変更は下記）。大きな関数は宣言と局所分岐を返す。bundle／scope_limited／capture_omitted／pending等を別々に確認し、一覧から必要な未選択範囲だけを追加する。返却済みの本文・行番号を再利用し、全ファイルreadやrepeatで探索全体を復元しない。128未満・明示context・旧来エンコードはreviewで使えない。既定24,000／最大26,000は維持する。

この版の評価はRTK＋rgを2026-10-16-discovery-live-abの5件へ固定し、smartだけを追加5件実行する。新たなRTK実行と混同せず、キャッシュ・時間帯・調査計画の変動が残る履歴比較として扱う。

## 0.11.0: ファイル選別後のreview

ディレクトリのreviewは、1ファイル16一致行までのプレビュー＋パスをBM25で評価し、上位3ファイルかつ最高点の25%以上に絞ってから原文を再検索・関数展開する。rank_query省略時は検索語を使う。明示ファイルは選別しない。未選択ファイルはreview_fileで案内しpending/既読にはしない。候補捕捉上限は別に残る。preview_omittedは順位付け用プレビューの省略であり、選択ファイルは再検索する。

同じretrieve全体で実装8・テスト6・補助/型8・定数16の枠を共有し、同じ要求で選択済みの範囲も候補から外す。別の必要事項は狭い追加取得で補える。一般名stage/verify等だけのroot全体テスト補完を止め、モジュール参照・具体的な実装名を使う。テストだけの要求からroot全体のテストへ展開しない。既知の小さなモジュールは必要なテストと一緒にreadしてよい。パスは返却された原文/hintを使い、推測したパスで独立バッチを失敗させない。

24,000/最大26,000の枠に加え、返却96,000バイトの上限を既読記録前に適用する。返せない行はpendingに残し、後付けの切り詰めはしない。外側30,000の計数との余裕であり、任意のクライアント上限での非切詰め保証ではない。一般化した節約効果は実測を要する。

ファイル順位付けはBM25にパスの事前重みを適用する。src/lib配下の実装は2倍、テストは0.5倍、その他は1倍とし、補助的な評価スクリプトより実装を優先する。ハード除外ではなく、明示ファイルには選別を適用しない。この命名規則が合わないプロジェクトでは未選択hintから必要なファイルを指定する。

## 0.12.0: 文書・出力契約とモジュールの取得

`-e --stream`およびMCPのハイフン開始パターンを値として扱う。文書のreviewは見出し区間（最大120行）か局所文脈を返し、locateへのやり直しを不要にする。既定review探索にMarkdown等を含め、明示ファイルの拡張子は制限しない。コードがある広い探索ではコードを優先し、文書も必要なら同じバッチの別操作でパス/globを指定する。

ファイルのプレビューは先頭固定から、クエリ語を多く含む行を最大16行まで保持する方式へ変えた。製品関数名の語との対応とファイルの大きさも採点し、広いreviewは最上位のsrc/lib/testモジュール系列へ絞る。別系列はhintに残し、明示パスで取得できる。命名規則による推定であり、必要な全モジュールの判定ではない。

JSON/schema調査では、読み込んだコードが64KiB以内なら、必要なソースと同じディレクトリのシリアライズ定義を最大2関数補完する。JSONリテラルの具体的なキーを複数検証するテストも関連候補に加える。既存の実装8/テスト6/補助8/定数16と大きなトークン枠・96,000バイト上限は維持する。関係は字句上の推定で、テスト実行や完全なスキーマ検証を意味しない。

JSON/schemaに直接対応するテストは既存6枠のうち最大2枠を優先する。補完するシリアライズ探索は同一ディレクトリの16KiB以下・最大8候補ファイルに限定し、実際のキー定義を持つ関数を選んでから順位付けする。JSONパーサーの参照だけで出力定義が隠れないようにする。


## 0.14: ローカル埋め込みとAST

`review`は、`JRG_EMBEDDING_SOCKET`が設定されている場合だけ、ローカルのEmbeddingGemma 2候補をBM25の候補へ加え、ファイル単位のreciprocal rank fusionで順位を決める。未設定時は従来の語彙検索を使う。`locate`、通常検索、正規化・機械出力は埋め込みを使わない。

`scripts/embedding.py`は、公式`google/embeddinggemma-2`のリビジョン`914f7f89142e33e77833254d9c9b90c3cef7303b`をローカルファイルから読み込むUnix socketサービス。モデルの取得は別操作とし、実行中は`local_files_only=True`。別モデルや外部APIへの切替はない。ライセンスはApache 2.0。sentence-transformers 6.1以降、transformers 5.18以降、PyTorch、Pillow、Torchvisionが必要。引数は`--help`を参照。モデル・SQLiteキャッシュ・socket・ログはGit管理外の専用ディレクトリに置く。

テキストのみの768次元・float32で実行し、文書は公式`Document`、クエリは`CodeRetrieval`のprefixを使う。候補用の窓は最大80行/4,000文字、20行重複（単一の長い行は1行）。モデルの最大入力は2,048トークンで、超過する窓は候補ベクトル作成時に切れる。返す根拠は原文から取得し、切れたベクトルを完全な証拠とは扱わない。索引はファイル内容・モデル版・prefix・分割方式でキャッシュし、毎回現在のソースを確認する。1回の索引対象は最大8,192ファイル/64 MiB、各ファイル最大4 MiB。非UTF8・バイナリ・symlinkを除外する。

クライアントは要求パスとglob・ignore設定から対象を決め、範囲外の候補を拒否する。返された行と現行原文が異なれば語彙検索へ戻る。接続失敗・120秒の待機上限・入力上限も明示してフォールバックする。索引作成時間・検索時間・新規埋め込み数をサービスのログへ記録する。

関数・分岐範囲にはast-grep-language 0.45.1のRust/TypeScript/TSX/JavaScript/Python parserを使う。構文エラーや未対応言語では従来の範囲推定を使い、`scope_parser=lexical fallback`を表示する。関連テストの選択・同一ファイルの補助定義の追跡は引き続きheuristicであり、ASTによる意味的な依存関係の網羅ではない。
