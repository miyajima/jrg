# 頻出表現ルールの実装と、新しい未評価資料での自動英語の検証

2026-10-22。版付きの頻出表現ルールを共通APIへ実装し、原文を渡さず生成した英語を、別の公式資料8件で比較した。

主比較の1,024トークンでは、従来方式の指定根拠保持が **11/17（64.7%）**、改善した英語生成と組み込みルールを使う条件が **13/17（76.5%）** だった。全指定根拠が残った資料は **4/8→5/8**。同じ英語へルールだけを追加した条件では、指定根拠数の増加はなかった。

2,048トークンでは **13/17→16/17（94.1%）**、全指定根拠が残った資料は **5/8→7/8**。改善は確認できたが、今回の資料全般でルール単独の効果があったとは言えない。生成指示ごとに1バッチの自動生成なので、指示そのものの一般的な効果と生成のばらつきも分離できていない。

## 実装した内容

- [版付きJSON](../../data/query-expansions.v1.json)の初期8ルール: 0以下・0以上・厳密に正・厳密に負、上限なし、レート制限、指数的な再試行待機、S3の正式なバケット種別名。頻出を想定した初期対象で、Web全体での出現頻度を測定したものではない。
- 質問と呼出元の追加表現だけに照合し、原文をルール生成に使わない。完全な語句と対象条件で照合し、直前のnot/never/withoutは保守的に除外。追加した語句から別ルールを連鎖させない。
- 元の質問・追加表現を保持。自動追加は最大4表現・512バイト、全体4,096バイト以内。追加が収まらなければ元の入力を切らず、その追加を省く。無効化はCLIの`--query-rules off`、APIの`QueryRuleMode::Off`。
- MCPの英語生成指示に、原文を見る前の生成、意味が明確な正式用語・数値境界の同義表現、回答事実の追加禁止を明示。jrg自体は外部モデルや翻訳サービスを呼ばない。
- [更新手順](../../data/QUERY_EXPANSIONS.md)を追加。JSONの版更新、正例・反例のテスト、既知資料での回帰確認、別の未評価資料、再ビルドとプロキシ再起動を一組にする。定期的な改善時に同じ手順で追加できる。自動採用・本番書き換え・定期ジョブの作成は行っていない。

## 事前に固定した比較

| 条件 | 質問から自動生成した英語 | 組み込みルール |
|---|---|---|
| A: 従来方式 | 従来の指示 | 無効 |
| B: ルールのみ追加 | Aと同じ英語 | 有効 |
| C: 生成指示も改善 | 数値境界・正式用語も意識する指示 | 有効 |

日本語の主質問は全条件で保持。二つの履歴なしAIに日本語の質問と各指示だけを渡し、URL・原文・正解・他方の出力・ルール表を渡さなかった。道具も禁止した。各1バッチの英語を修正・再生成せず、本文取得前に固定した。正確なモデル版はツールから報告されず、ホストから継承したことまで確認できる。

生成指示の全文と出力は保存している。製品のMCP説明は、改善指示に既存契約を明示する「Do not add facts.」を付け足したもの。採点後に英語やルールを調整していない。

新しい8ページは、過去二つの評価のURLと重複0件。原本・抽出後・時刻・ハッシュを保存し、選定前に8問17根拠単位を固定した。独立担当が、参照する23ブロックと原本HTMLを照合し、質問の全条件と代替箇所を監査した。最初の取得は保存先ディレクトリ不足で保存に失敗したため、同じ8URLを再取得した。取得先の差し替えはない。

1,024と2,048の2予算、8資料×2予算×3条件の全48結果を各1回実行。原文・質問・英語・正解・ルール・コード・バイナリを選定前に固定し、実行後も一致した。技術資料に絞った目的抽出であり、無作為なWeb資料の標本でも、モデルが学習で見ていない資料の保証でもない。

## 残った課題と解釈

- **新規資料での上積みは主に生成表現の違いを含む条件で生じた。** GCSの改善英語には、原文を見ずに生成した`jitter`という用語が含まれ、1,024でバックオフと冪等性の両根拠が残った。ただし一語だけを操作した診断ではないため、その単語だけを改善原因と断定しない。
- **Queueは周辺情報との組が揃わない。** 1,024のCでも、容量やputの条件を説明する本文`line-47`・`line-112`は残っているが、クラス定義`line-45`・メソッド署名`line-110`が落ち、事前指定の組が成立しない。2,048では容量の組だけ揃った。これは情報がすべて消えたという意味ではなく、設定名・署名と説明の対応を保つ課題を示す。意味上の情報保持に対して採点が保守的な可能性もある。
- **GNU timeoutの小数指定、NGINXのnodelay**は1,024では落ち、2,048では全条件で残った。言い換えだけですべての条件を保持する保証はない。
- **予算と保持数は単調ではない。** SSHのA/Bは、1,024で揃った設定名と説明の組が2,048では揃わなかった。候補の原子性・周辺情報の詰め方も影響し、予算を増やせば常に同じ根拠が残り続けるとは限らない。
- **初期ルールの範囲は限定的。** 登録語句にない数値表現や別APIの用語は補完しない。出力結果を見て今回のルールを増やして得点を上げることはせず、以後の改善候補として扱う。

## 既知資料の回帰と機械検証

前回の8資料は開発・回帰用として別集計した。ルール無効時は以前の8出力と完全一致。有効時はRedisが1/2→2/2、S3が2/3→3/3で、他6資料の指定根拠は保持された。合計14/17→16/17だが、これは新規資料での効果の証拠には含めない。[回帰結果](regression_results.json)

root **222件**、MCP **16件**、RTK **19件**、fmt・clippyが成功。数値境界、否定・識別子・対象API、非連鎖、追加数とバイト数、無効化、3アダプターの新しい動作は、失敗するテストを確認してから実装した。再利用検索はDBを開けず通常実装した。既存テストは、サンドボックスのローカルTCP禁止と標準出力への履歴UUID混入で最初に停止したため、ローカル模擬サーバーを許可し、この実行だけ`JRG_HISTORY=off`にして全件確認した。履歴専用テストは自身で環境を設定する。履歴機能・既存の出力比較テストは変更していない。[チェック記録](checks.json)

全48返却で、原文・URL・タイトル・ハッシュ・親見出し・関連ブロック、正確な`o200k_base`トークン数と予算、採点・集計を保存結果から再確認した。入力ページJSONは合計38,401トークン、1,024のCは返却JSON合計8,095トークン。これはコンパクトJSONの測定で、英語生成を含む全実行コストや請求額の削減率ではない。[照合結果](verification.json)
