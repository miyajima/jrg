# 改善英語だけの場合と、ルールを併用した場合

2026-10-22。ユーザー依頼で不足していたD=改善英語・ルール無効を追加した。**今回の8資料では、指定根拠保持に対して改善英語だけで同等以上の結果だった。ルールの追加効果は確認できず、2,048トークンでは1単位悪化した。**

## 全4条件

数字は事前指定した根拠17単位の保持数。英語・原文・正解・エンジン・ルール表は前の評価から変更していない。

| 英語表現 | ルール | 1,024トークン | 2,048トークン |
|---|---|---:|---:|
| 従来の自動英語（A） | 無効 | 11/17 | 13/17 |
| 従来の自動英語（B） | 有効 | 11/17 | 13/17 |
| **改善した自動英語（D）** | **無効** | **13/17** | **17/17** |
| 改善した自動英語（C） | 有効 | 13/17 | 16/17 |

全指定根拠が残る資料数は、1,024でA/B/D/C=4/8・4/8・5/8・5/8、2,048で5/8・5/8・8/8・7/8。

- **英語表現の差（A→D、ルール無効同士）**: 1,024では+2単位、2,048では+4単位。悪化した資料・失った指定根拠はなかった。
- **従来英語でのルール効果（A→B）**: 両予算とも指定根拠数の増減なし。
- **改善英語でのルール効果（D→C）**: 1,024は全8資料で同じ指定根拠。2,048は7資料同じ、Queueだけ2/2→1/2で、`put-timeout`単位を失った。新たに得た指定根拠はなかった。

保持数が同じ条件でも、返される他の段落やトークン数が同じとは限らない。主張は固定した指定根拠についてであり、最終回答精度や費用の評価ではない。

## どこに差が出たか

| 資料 | 1,024: 改善英語のみ / ルール併用 | 2,048: 改善英語のみ / ルール併用 |
|---|---:|---:|
| Python Queue | 0/2 / 0/2 | **2/2 / 1/2** |
| asyncio Semaphore | 2/2 / 2/2 | 2/2 / 2/2 |
| GNU timeout | 2/3 / 2/3 | 3/3 / 3/3 |
| OpenSSH | 2/2 / 2/2 | 2/2 / 2/2 |
| GitHub REST rate limits | 2/2 / 2/2 | 2/2 / 2/2 |
| NGINX | 1/2 / 1/2 | 2/2 / 2/2 |
| Cloud Storage retry | 2/2 / 2/2 | 2/2 / 2/2 |
| Java BlockingQueue | 2/2 / 2/2 | 2/2 / 2/2 |

Queueの2,048では、ルール無効時は`Queue.put(...)`の署名`line-110`と説明`line-112`が両方残る。有効時は説明だけが残り、事前指定の組が成立しない。容量の設定名・説明`line-45`・`line-47`は両条件で残る。同義語を増やすと順位付けと詰め込みの対象も変わるため、根拠保持が必ず改善するわけではない。どの追加語がこの差を生んだかを一語ずつ切り分ける実験はしていない。

前の評価でC対Aの改善を確認しただけでは、ルールの上積みを判断できなかった。今回Dを追加すると、改善した英語表現だけで、その上積みを同等以上に得られると分かった。英語表現の指示ごとの生成は1バッチなので、生成指示一般の因果効果と生成のばらつきは引き続き分離できない。

## 採用判断

現時点では、**改善した英語表現を基本にし、ルールの常時併用は控える**方針が妥当と考える。版付きルールの追加機構は、未登録の表現で実際に失敗したときの対策候補として使い、適用前に同じ英語で有効/無効を比較する。

既知のRedis/S3では従来英語へルールを足す効果があったが、これは開発・回帰用の結果であり、今回の改善英語や他の資料でルールが有益という根拠にはならない。ルール全般が無効だと断定することもできない。

この追加作業は比較検証のみで、製品の既定値は変更していない。現在の既定は組み込みルール有効であり、CLIの`--query-rules off`、APIの`QueryRuleMode::Off`で今回のD条件を使える。
