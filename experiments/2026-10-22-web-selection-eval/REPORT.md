# 実Web検索によるjrg選定評価

2026-10-22。結論は、**本文の選定には改善を確認したが、検索結果一覧の再選定の改善は確認できず、日本語の質問と英語資料の組み合わせでは悪化する場合がある**。この結果だけでWeb検索全体に効果があるとは言えない。

## 1,024トークン予算での結果

| 対象 | 元の順序で選定 | jrg | 評価したもの |
|---|---:|---:|---|
| 本文・資料と同じ言語 | 50.0% (5/10) | **90.0% (9/10)** | 指定した根拠ブロックの保持率 |
| 本文・日本語の質問と英語資料 | 55.6% (5/9) | **22.2% (2/9)** | 同上 |
| 検索結果一覧・資料と同じ言語 | 15.0% (3/20) | **10.0% (2/20)** | 指定した公式資料URLの保持率 |
| 検索結果一覧・日本語の質問と英語資料 | 18.2% (2/11) | **18.2% (2/11)** | 同上 |

本文・同じ言語の5ケースでは、すべての指定根拠が残るケースも2/5件から4/5件に増えた。jrg出力は合計4,065トークンで、全件の本文入力JSON 19,045トークンから78.7%減った。比較対象の元順序方式も4,405トークンに減らせるため、単なる削減率だけがjrgの効果ではない。同じ予算で指定根拠を多く残した点に改善がある。

検索結果一覧では、jrgは合計49,872→5,828トークン（88.3%減）に圧縮したが、元順序方式は5,577トークンで公式資料の保持も上だった。検索結果一覧の段階では、今回jrgを使う品質上の優位は得られなかった。

## データと比較方法

- 実際のWeb検索ツールを6回使用。Rust、Python、Node.js、GitHub Actions、JR東日本、気象庁の106候補を保存した。検索サービス内部の全候補や通常の短いスニペットだけの応答ではなく、ツールが返した長い抜粋・本文を含む範囲を対象とした。
- 公式本文は5テーマを使用。元HTML・URL・取得時刻・SHA-256を保存し、外部形式の変換として一般的なHTML解析でMarkdownにした。jrgによる検索・スクレイピングは行っていない。JR本文はHTTP403で取得できなかったため本文評価から除外し、ゼロとして数えていない。気象庁FAQは補助取得として保存したが、本文評価には用語定義ページを使用した。
- 質問は19種類。検索10、本文9。同じ技術資料4テーマに日本語の質問も設定した。独立したテーマは6種類であり、19種類や3予算を独立した多数のWebタスクとして扱わない。
- 512/1,024/2,048トークンの3予算。57組の比較、各方式合計114結果。jrg CLIは各条件3回（171回）実行し、結果の一致を確認した。3回の反復は決定性・参考の時間計測で、独立サンプルを増やすものではない。
- 元順序方式もjrgと同じ正規化済み文書・親見出し・関連注記の集合・出力JSON形式を使用。検索順位または本文順で、入る集合を順次採用し、入らない集合は飛ばして後続を試す。表や関連注記を途中で切らない。
- 予算はメタデータを含むコンパクトJSON全体を、既存のo200k_base Counterで計数した。全114結果で予算・原文ブロック・出典ハッシュ・依存関係の一致を確認した。
- 選定エンジン、アダプター、CLIのコードと実行ファイルのハッシュは実行前後で同じだった。評価コード・データ・補助exampleのみ追加した。

## 改善・失敗の具体例

- Node.jsの英語の質問では、本文の後方にある同期読み込みの条件、依存先のtop-level awaitによるエラーと代替手段を、512トークンでも両方残した。元順序方式では2,048トークンでも両ブロックが入らなかった。
- Pythonの英語の質問では、1,024トークンでGILの明示的な有効化と拡張モジュールによる自動有効化の両方を残した。元順序方式では両方とも入らなかった。
- 日本語で尋ねたRustでは、1,024トークンのjrg出力に必要なエディションの記載がなかった。Node.jsでも該当エラーと代替のimport()が残らず、GitHub Actionsでもqueue: maxや実行中のキャンセル条件が残らなかった。英語の語彙と日本語の言い換えをBM25だけでは十分対応付けられない。
- 気象庁の根拠を含む表は、表単独で3,635トークン。表全体を1ブロックとして扱うため、今回の最大2,048トークンの予算にも入らず、両方式とも保持できなかった。行や意味上のまとまりへ分けつつ見出し・注記を保持する対応が必要。
- 検索ツールが返す長い結果も1候補1ブロックのため、上位の公式資料が予算に入らず、短い別候補へ置き換わることがある。検索サービスの順位を保つ設計や、長い候補内の選定との分離が次の検討点。

## MCP・RTKを通した実データの再生

実際に取得したPython検索結果とNode.js本文を、保存コーパスを返すローカルMCPと模擬HTTP上流へ再生した。実装済みのMCPプロキシとRTK実ルーターの4経路すべてで、受信した選定JSONが直接CLIと一致した。実検索サービスとのライブMCP接続、実モデルAPIへの送信は実施していない。

| 実データ | 入力JSON | MCPのresultオブジェクト | RTKのtool_resultブロック |
|---|---:|---:|---:|
| Python検索結果 | 8,461 | 978 | 1,024 |
| Node.js本文 | 10,021 | 1,040 | 1,086 |

単位はo200k_baseトークン。選定JSON本体の予算は1,024。MCP/RTKの外側の構造は予算外なので、転送全体が1,024以下になる保証はない。模擬上流のusageはテスト用の値で、課金計測に使っていない。

MCP列はJSON-RPCのjsonrpc/idを除いたresultだけ、RTK列はリクエスト内のtool_resultだけを数えている。JSON-RPC全体、モデルへのリクエスト全体、HTTPヘッダーを含む通信量の計測ではない。

## 解釈の限界

検索の正解は人手で指定した公式URLの保持であり、すべての関連URLや本文中の正答を採点したものではない。本文も特定の原文ブロックを正解とし、別の場所にある同義の根拠は自動加点しない。したがって回答精度の90%を意味しない。上記の日本語3ケースは出力中の具体的な根拠語も確認したが、全出力の意味を網羅的に採点したものではない。

比較対象は文脈の集合を元順序で詰める方式1種類。高性能な別のrerankerとの比較ではない。モデルに回答を生成させる比較、実際の請求額、プロンプトキャッシュ、全処理の高速化は未検証。CLI時間はresults.jsonに参考記録したが、バックグラウンド負荷を制御しておらず速度改善を主張しない。

本格的なWeb検索結果選定への採用を判断するには、言語をまたぐ関連付け、検索順位の利用、大きな候補・表の分割を改善した後、別テーマの未使用データで再評価する必要がある。

## 監査と再実行

最初の評価入力には別ページのタイトル、引用行スニペットの欠落、空タイトル候補の混入という変換上の誤りがあった。独立レビューで検出し、失敗する回帰テストを作って修正。最初のコード・固定入力・全結果はattempt-1-metadata-contaminated/へ保存し、効果の判断には使用していない。質問と正解の指定を変更せず、入力を再固定して全件を測り直した。本報告の数値は修正後のresults.json/summary.jsonのみ。

```sh
cargo build --offline --bin jrg-select --example web_selection_eval_support
python3 -m unittest discover -s experiments/2026-10-22-web-selection-eval -p test_evaluate.py -v
python3 experiments/2026-10-22-web-selection-eval/evaluate.py run
python3 experiments/2026-10-22-web-selection-eval/transport_check.py
```

Webへの再アクセスをせず、保存した固定入力で再現できる。runはoutputs/results/summaryを上書きするため、別の試行を残す場合は先にコピーする。元の検索返却はraw/search-*.txt、HTMLと取得情報はraw/page-*.htmlとfetch_manifest.json、質問・正解はcases.json、固定入力のハッシュはfrozen_inputs.sha256.jsonを参照。
