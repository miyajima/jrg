# jrg 0.3.0の自動選択とRTK込みの比較

確認日: 2026-10-15 JST。`--smart` を実装し、このMacへ更新導入した。既存の通常検索と `--ai` の出力契約は維持し、新しい動作は `--smart` で有効にする。

## 実装したこと

- `--engine auto|native|rg`。smartモードの正規表現・非正規化の原文検索は、対応するファイル入力ならrgを選ぶ。NFKC・カナ統一が必要なら内蔵側へ残す。ASCII検索でも原文の全角を拾う意味を保つため、文字種だけで切り替えない。
- `--intent explain`。明示した文脈フラグがなければ前後3行を追加する。`-A/-B/-C` の明示指定を優先する。自然言語から検索式を生成する機能ではなく、離れた呼出先まで自動追跡する機能でもない。
- smart出力は短い完全な通常形式と、完全性を保つ圧縮形式を比較する。通常形式が予算内で、圧縮側では本文・文脈が切れる場合は通常形式を優先する。明示した1ファイルなら通常形式のパスを省く。通常形式の保持バッファは8 MiBまでで、超過時は圧縮側へ進む。
- 大きい結果には既定2,000トークン・320書記素の上限を適用する。本文の `omitted/clipped` に加えて文脈の `context_omitted/context_clipped` を表示する。すべての証拠が残ることを保証する上限ではない。
- rgを `--no-config --json --no-require-git --crlf --encoding utf-8` で起動し、元のglob、大小文字、文脈等を渡す。JSONを既存のjrgイベントへ変換する。標準入力・別文字コード・JSONなどの専用出力・改行パターン等は内蔵側へ残す。
- rgがない場合のautoは内蔵へ戻る。起動済みrgの検索エラーは再検索せず返す。強制rgと非対応条件の組合せはエラーにする。子プロセスは通常終了・準備中のエラー時ともに回収する。
- `--explain-plan` で実際のエンジンと理由・文脈量をstderrに表示する。選択は保守的な規則であり、すべてのタスクで最少入力を保証する最適化器ではない。

```sh
jrg --smart がっこう ./docs
jrg --smart --regex --intent explain 'initial_input_deadline_control' ./src
jrg --smart --regex --intent explain -A 6 'reserve|claim' ./src
jrg --smart --regex --explain-plan 'fn deadline' ./src
```

## 同じ5課題での出力比較

前回の固定ソースと、問いに必要な17項目を再利用した。検索式・対象ファイル・明示した文脈は全方式で同じ。stdout全体を `o200k_base` で数えた。元の5課題はソースを見て設計した回顧的な課題であり、自律モデルの初見タスクではない。

| 方法 | 最終stdoutトークン | 必要な情報 |
| --- | ---: | ---: |
| 調整したrg | 550 | 17/17 |
| 調整した旧AI形式（内蔵検索・320書記素） | 722 | 17/17 |
| 新しいsmartモード（この5件はrgを選択） | 548 | 17/17 |
| RTK 1.0.1 + 調整したrg (`rtk rg`) | 550 | 17/17 |
| RTK 1.0.1のrunner + smart (`rtk run jrg …`) | 548 | 17/17 |

新smartは旧AI形式より **24.1%減**、RTK+調整rgより **0.36%減**。この短く調整済みの5件では、RTKやjrgを重ねる大きな追加削減はなかった。2トークンの差は離れた文脈ブロックの区切り表示による。大きな改善率として一般化しない。

`rtk run` はjrg専用の圧縮フィルタではない。このMacのRTKヘルプと実出力では、smartのstdoutがそのまま返った。「RTK+jrgで二重に圧縮した」という結果ではない。

共通フィルタも別に確認した。5件のsmart結果に出典ヘッダーを添えてまとめ、`rtk pipe --filter grep` に渡した1試行では **610→610**、17項目を保持、終了コード0、stderrなし。この610は出典ヘッダーを加えたバッチであり、表の548と同じ入力ではない。

## RTK試験の記録と限界

ローカルのRTK手順に従い、新しいオプション形はbeginで試験を予約し、各1回の出力から判定した。入力を変えて同じ試験を繰り返していない。すでに許可されていた `rtk rg -n` の判断は変更していない。新規形で必要項目の保持に対する追加圧縮がなかった組合せは、既存のルーティング記録へblacklistとして記録した。RTK自体やフック、共通ハーネスを改変していない。

最初のaudio_limitケースで、記録処理のオプション順が予約時と一致せず中断した。取得済みstdoutとstderrを保ち、同じRTK実行を繰り返さず元の予約を確定した。表の初回2つのRTK出力のトークン数と内容は実測だが、元の終了コードのメタデータは未保存。残る4課題のRTK終了コードはすべて0。最終版のsmart実行は5件とも0で、RTK試験時に保存したsmart stdoutとバイト単位で一致することを確認した。最後のCRLF・改行パターン対応修正でも、この5件の出力は変わっていない。

評価対象は検索・読取の出力であり、モデルの総入力、累積会話の再入力、推論、キャッシュ、費用、実ターン数ではない。各段の削減率を足さず、最終出力と必要な再取得の出力を同じ条件で集計すべきである。ここでは17項目が初回に揃ったため、定義済みの追加再読取は0。実タスクでの正解率や再調査ターン削減率は未測定。

## 日本語検索と出力制限の価値

`ガッコウ` / `ｶﾞｯｺｳ` / `がっこう` / 結合濁点の4行に対し、`jrg --smart がっこう` は4行すべてを返した。同じ文字列の `rtk rg -n -F がっこう` は1行。これは検索意義の違いであり、1行だけの方を「トークン削減に成功」と評価してはいけない。結果は `japanese.json` に保存した。

**jrg独自の価値は日本語を含む表記ゆれの正規化にある。出力予算の制御は言語を問わず使えるが、短いコード検索では調整したrgやRTKと効果が重複しやすい。** 正確な全件列挙や不存在確認は圧縮しない通常の検索を使う。日本語であっても正規化不要の原文検索ならrgの経路でよい。

- 追加11テストが、エンジン選択、rg不在のfallback、失敗時の再検索禁止、条件・戻り値の文脈、明示した文脈0、予算、文脈欠落表示、空結果、旧機械出力との衝突を確認する。
