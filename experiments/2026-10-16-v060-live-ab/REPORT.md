# jrg 0.6.0とRTK＋rg：同じ5課題の実モデル比較

2026-10-16 JST。固定した5課題で両方式を新規に実行した。**総入力は5.7%減、モデル応答は39→37回。ただし時間は2.1%増えた。** 音声は入力9.1%減・応答2回減、日本語互換性は入力11.3%減・応答同数。各課題1ペアの記述的結果であり、安定した削減率の保証ではない。

## 条件と測定

- AはRTK＋rg。Bはjrg 0.6.0 smart。5課題×2方式、計10実行。過去の試行は保持し、今回に混ぜていない。
- OpenAI `gpt-6.1-sol`、reasoning effort `high`。実際のセッションでもモデル名・設定を確認。バックエンドの不変リビジョンまでは固定できない。
- 前回と同一のjrg・sfk-shinsa・ConsentSide・Astra Harnessの固定ソース。両方式合計2,992ファイル。調査対象のjrgソースは従来の固定版であり、検索道具の0.6.0と区別した。
- Aの指示・rg/RTKバイナリ・検索ラッパーは0.5比較と同一。Bは0.6.0バイナリと、実際の既定予算8,000/16,000/24,000および非連続範囲見出しの説明を使用。方式全体の比較であり、単一変更の因果効果ではない。
- 300秒/実行の上限で順次実行。タイムアウト、自動再試行、追加採点モデルはなし。
- 総入力は各応答のprovider記録をresponse_idで重複排除して合計。**cached inputを含む**。調べ直し、確認、出力切れからの回復を含む全応答を数え、失敗コマンドも除外しない。各試行でCLI最終使用量と一致した。
- 応答回数はモデル応答数。ユーザーターンは各方式5回。検索数・シェル呼出し数は別指標。時間はCLI起動から終了までの経過時間の合計で、親による準備・品質確認・Wiki作業は含めない。

実験用・導入済みjrgのSHA-256は `0dd6c9d6d5085b9cc2c6d88f538b453fb853fd45b240f57da7813cbf35b32e6b`。固定ソース、指示、バイナリ、ラッパーの終了後検証はすべて一致した。

## 音声の調べ直し

Bは8一括取得、1完全検索、1ファイル一覧の計10シェル呼出し。Aは26。Bは取得済み403行の重複返却を省いた。jrg側のdeferred/partialは0、resumeも0だった。最後に`--repeat`で取消処理・キュー・drain・関連fixtureなどを再取得する呼出しが1回あった。

外側のツール出力にはAで3件、Bで2件の明示的な切詰め通知があった。Bのうち1件はファイル一覧、1件は内容出力。内容の切詰めは、jrg予算17,000、内側exec_commandの上限24,000を指定していても、外側functions.execの既定10,000で12,830トークンの返却が切れたものだった。jrgがstdoutへ書いた範囲をモデルもすべて見た、とはいえない。repeatと切詰めの両方は観測できるが、repeatの全範囲が切詰めだけを原因としたと断定しない。

Bは早い段階から広いbatchを使い、Gemini adapterの汎用的な完了条件regexをexplainへ渡して多数の関数・テストまで取得していた。モデル最終応答の入力はA87,655、B91,008。Bは各応答の文脈が大きめでも応答を2回減らしたため、累積入力では9.1%減になった。全実行時間は15.137秒増えた。音声Bの出力も6,322→6,897と増えており、今回の時間差を検索エンジン単体の速度差には帰属できない。

両方式とも重要な静的リスクを保持した。対象Aのfetch待ち中にBが登録される順序で、A取消がBのeffect IDまで取消済み集合へ入れる経路と、Gemini受付120秒に対して実streamが90秒PCM・既定100秒timeoutである不一致である。再現実行や実デバイスでの保証とは区別されていた。

## 日本語互換性の調べ直し

Bはファイル一覧1回＋一括取得4回。初回にnormalize/search/outputの既知範囲をまとめ、以後CLIテスト、引数、エラー処理、rg適合条件、実rg比較テストを追加した。取得済み56行を省き、deferred/partial/resume/repeatはいずれも0。内容出力・一覧とも明示的な切詰め通知はなかった。

Aは18シェル呼出しで、検索後にnormalize全文、search/output、テストなどを読み、後で一部テスト範囲を再読取していた。明示的な出力切詰めが1件あった。Bの最終応答入力は38,656でA50,951より小さい。一方、ファイル一覧・本体・テスト・追加条件・最終確認という調査段階は残り、モデル応答はどちらも6回だった。したがって**日本語の予算往復はこの試行で発生しなかったが、モデル応答自体は減っていない**。

両方式はNFKC→カナ、書記素からの原文位置復元、正規化後smart-case、デコード後UTF-8バイト位置とスカラ列、厳格な明示エンコード・BOM/CRLF、初期NUL判定と静的テストの限界を正しく区別した。

## 残る往復と次の改善候補

Bの全5課題で予算によるdeferred/partial/resumeは0。重複返却の抑制は合計1,019行。ただし行数は省略カウンタの合計であり、独立したファイル行の一意集合や入力トークン削減量ではない。

土地候補は入力17.1%増・応答1回増だった。大きな初回取得と広い説明検索に加え、外側出力上限による切詰め2件、明示repeat1回が残った。jrg側予算を小さく戻すことより、次の2点が未測定の改善候補になる。

1. 内側exec_commandだけでなく外側functions.execの`max_output_tokens`も合計出力に合わせ、コマンド結果オブジェクト全体ではなく必要なoutputを返す。大きなjrg枠をモデル可視範囲まで通す。
2. 汎用regexのexplainで多数の大関数を取得する前に、必要な関数名・テスト名と既知の読取範囲へ絞り、独立した追加確認を同じ応答内にまとめる。

この候補は本試行中には導入していない。結果を見たあとに指示やツールを変更して同じコホートの途中へ混ぜていない。1ペアの差にはモデルの確率的な調査方針や実行時の負荷も含まれる。

参考として前回0.5のBは音声645,570・11応答、日本語261,017・8応答だった。今回Bはそれぞれ604,954・10応答、174,086・6応答へ改善したが、A側も変動しているため、版変更だけの因果効果とはしない。主結論は今回の新規A/Bである。最初の39検索stdoutの9.7%やオフライン固定要求の7.6%とは測定単位が異なる。

## Wikiエラーの原因

前回のMCPエラーは`wiki_engine_unavailable: install the matching OrgBrain native package or run build:wiki`だった。現在のMCP設定はattempt-pilot-current経由でcli-compat-287ae6-20261016のJS実行環境を参照するが、そのエンジン探索候補にdarwin-arm64のorgbrain-wiki-engineが存在しなかった。一方、設定済みのWiki専用wiki-20261001環境には実行可能なエンジンが存在した。MCPと専用Wikiの実行環境の不一致であり、エラーメッセージはデータ破損を示していない。共有MCP設定の書換えやインストールは行っていない。
