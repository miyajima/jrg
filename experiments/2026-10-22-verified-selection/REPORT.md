# 改善英語を標準にし、承認済み条件だけにルールを適用

対象は検索・取得済みデータの選定。検索サービスや翻訳モデルを追加する変更ではない。呼び出し側AIが原文を見る前に英語を生成する既存経路へ、改善した生成指示を標準として提供する。互換性のため英語は任意入力のまま。

## 実装

- 共通APIの`select()`とCLIの既定を`verified`へ変更。未登録の条件は呼出元の英語だけを使用する。
- 承認台帳は、質問・英語・予算・解析済みの全原文を含むリクエストのSHA-256に、比較済みのルール集合と証拠を結び付ける。本文は一致照合に使い、英語やルールの生成には使わない。同一入力に別の承認を合成しない。
- 初期の承認はRedisの`nonpositive`とS3の`s3-general-purpose`について、従来の英語と記録済み資料・1,024トークンの2条件だけ。サービス全般への有効化ではない。コード・依存関係・カタログ変更後は再検証を要求する。外部入力やホットリロードで承認を追加できない。
- 全カタログの`builtin`と部分集合の`--rule-ids`は比較実験用。MCPとRTKは明示的に`--query-rules verified`を指定する。
- MCPは`jrg_focus_en`へ改善指示を表示し、選定へ渡した後、上流ツールの引数から除く。RTKはクライアントが事前に宣言した文字列型の`jrg_focus_en`の説明だけを更新する。RTK側でクライアントが知らない引数を追加することはできないため、この宣言がないクライアントでは既存の英語生成・メタデータ対応が必要。
- RTKは起動時のセレクター絶対パス・実体のSHA-256を固定し、メモの再利用前にも照合する。起動後のバイナリ変更・差し替え・欠落からの追加はエラーにする。メモ条件にもポリシーと実体を含める。

## 比較結果

既存の凍結済み資料を再実行してポリシー変更を確認した。新しい未評価資料による追加の一般化評価ではない。過去の実験ファイルと凍結マニフェストは変更していない。

| 条件 | ルールなし | 新しい標準 |
|---|---:|---:|
| Redis・従来英語・1,024 | 1/2 | 2/2 |
| S3・従来英語・1,024 | 2/3 | 3/3 |
| 別の8資料・改善英語・1,024 | 13/17 | 13/17 |
| 別の8資料・改善英語・2,048 | 17/17 | 17/17 |

Redis/S3は承認する単独ルールで厳密に増加し、従来保持していた根拠を失わないことを確認した。質問・英語・予算・原文をそれぞれ変えた8条件は、ルールなしの結果と一致する。新しい8資料の16条件もすべてルールなしと一致し、以前の全カタログ適用で失ったQueueの根拠を保持する。保持単位の正解は以前に固定したものを使った。

全選定について元ブロック・出典・文書ハッシュ・関連ブロックの保持と、o200kによる出力トークン数が予算内であることを確認する。件数は根拠の保持であり、回答精度や請求額ではない。

証拠: [承認台帳](../../data/verified-query-rules.v1.json)、[Redis単独比較](redis-proof.json)、[S3単独比較](s3-proof.json)、[再実行の全結果](results.json)。

## 再現

```sh
cargo build --bin jrg-select
python3 experiments/2026-10-22-verified-selection/verify.py
```

コードやカタログを更新した際の台帳再生成は、比較結果をレビューしたうえで次を実行する。スクリプトは対象2条件の指定根拠が厳密に増え、失われない場合だけ台帳を書き、未知の条件を承認しない。

```sh
cargo build --bin jrg-select
python3 experiments/2026-10-22-verified-selection/verify.py --write-registry
cargo build --bin jrg-select
python3 experiments/2026-10-22-verified-selection/verify.py
```

台帳は比較済み入力だけを対象とする保守的な初期実装であり、一般的な質問にルールを広く適用する分類器ではない。将来対象を広げるには、対象条件の定義・正例/反例・無効時との比較を追加して再検証する。

## 接続検証

`transport_check.py`は実MCP stdioプロセスとコンパイル済みRTK HTTPプロキシを起動する。取得済み公式ページのRedis/S3/Queueと、ルール未承認・改善英語の2種類の模擬検索結果を使う。RTKの転送先はローカルの模擬プロバイダーで、外部モデルは呼ばない。

```sh
python3 experiments/2026-10-22-verified-selection/transport_check.py
```

MCPとRTKの各5条件、計10条件が共通CLIの出力と完全一致した。MCPは選定済みcontentだけを返し、調査目的・英語を上流へ漏らさない。RTKは同じ英語生成指示を転送し、元のtool_useを保ったまま履歴の再送でも同じ選定結果を返した。Queueでは署名・説明の両ブロックを保持した。[全接続結果](transport_results.json)を参照。

最終確認は本体227件、MCP17件、RTK26件のテストがすべて成功。両Rustプロジェクトのfmt・Clippyも成功した。ローカルソケットを使うテストとHTTP中継検証は、ネイティブの承認を通して実行した。実際の検索サービスへの再接続、外部モデルの推論、既存ユーザーセッションの再起動・設定変更は行っていない。

承認台帳の監査は、コンパイル済み台帳とファイルのSHA-256、承認ごとの証拠・原本・出力のハッシュ、固定正解による保持単位、正規化リクエストの一致を確認した。通常の再検証では証拠ファイルを上書きせず比較する。`verify.py --audit-only`でこの照合だけを再実行できる。[台帳監査](ledger_audit.json)と[最終チェック記録](checks.json)を参照。

英語やルールがどの未知資料でも改善することを保証する結果ではない。英語の自動生成は呼び出し側AIが担当し、今回の中継検証では過去に原文閲覧前に生成・固定した英語を再利用した。既存セッションへ新しい定義とコードを反映するには、ビルド済みバイナリを指定してプロキシを再起動し、ツール定義を再取得する。
